# ADR-0009: Full-screen display and compact guarded navigation

Status: Accepted for working-tree implementation
Date: 2026-10-10
Source: User-authorized Full Screen and Compact Navigation Specification.

## Decision

MainActivity enables edge-to-edge layout and owns Android system-bar presentation. A boolean `full_screen` in the existing `mavlab_app` preferences defaults to false and is changed through Ops → Display. Immersive mode uses transient system-bar reveal. Focus, keyboard transitions and multi-window state restore usable system bars. Bar visibility itself never triggers immediate re-hiding of a user-revealed bar. IME observation is attached to the content view; DecorView retains its platform inset handling and accessibility bounds updates.

The shell uses a full-width dock with four equally spaced, labelled selectable tabs. Content aims for 56 dp at default scale, with 22 dp icons and 12 sp labels. Height is intrinsic above the minimum, so large labels can wrap and increase height. The dock accounts for measured safe-drawing and mandatory-gesture insets; a viewport below four 48 dp destinations can scroll the dock horizontally rather than overlap hit regions. IME padding keeps Ops text entry usable.

Horizontal screen navigation uses `screenSwipeArea` on passive surfaces, with `screenSwipeExcluded` protecting nested controls. Cockpit and Ops register the full informational surface so cards, middle/lower content and gaps accept swipes consistently. Buttons, action rows, charts, switches, event filters and location configuration are excluded. Control and SIM retain narrower explicit passive regions to protect flight input and camera gestures. Bounds resolve live and are removed on disposal; exclusions win over any containing passive area. The detector observes Initial-pass down and movement, finishes each event in Final, and locks a dominant axis after the platform touch slop. A 1.2:1 dominance margin allows minor diagonal drift; ambiguous starts wait for direction rather than failing immediately. Once horizontal, the axis stays locked. Vertical intent or a descendant claiming movement before horizontal recognition cancels navigation. Multi-touch, system edges, touch exploration and visible IME are excluded. Modal dialogs own input in their own window.

A release commits one adjacent destination after 48 dp of horizontal travel, or a shorter flick with at least 24 dp of travel and 400 dp/second horizontal release velocity in the same direction, exceeding vertical velocity. The velocity threshold follows the [Compose snapping baseline](https://github.com/androidx/androidx/blob/androidx-main/compose/foundation/foundation/src/commonMain/kotlin/androidx/compose/foundation/gestures/snapping/SnapFlingBehavior.kt); the travel guard is a MAVLab choice. Distances use density, not screen width; Compose VelocityTracker includes historical touch samples. Tiny twitches, short slow movement and return-to-origin gestures do not navigate. Endpoints do not wrap. Updated page/enabled/callback state is read without restarting the pointer coroutine; animations do not introduce an input cooldown. A page or eligibility change during an active gesture cancels that gesture.

The stationary, clipped input container drives a Compose HorizontalPager with its generic user scrolling disabled. The existing passive-area detector is the sole touch-navigation owner. Ordinary page movement tracks horizontal finger displacement one-to-one; bounds stop at the sequence endpoints. Both visible page shells share one continuous scroll position. Release changes the target, not the current position, and a critically damped spring completes the remaining distance using release velocity. A new drag cancels settling and takes over the current position immediately. Cancellation, multi-touch or lost eligibility settles to the selected destination. Compose motion-duration scaling applies. Passive bounds resolve live LayoutCoordinates at touch-down.

Each page wrapper also clips to its own layout bounds. Viewport clipping alone cannot contain an offscreen SIM Canvas drawing at negative coordinates: the first grid line can escape into the right side of Control. Per-page clipping contains grid/trail overflow without removing the SIM overlay or changing gesture ownership, animation, preview preparation or lifecycle policy.

Unlike the superseded single-screen nudge, continuous paging composes incoming and outgoing UI shells together. One adjacent shell on either side is prepared ahead of the gesture: the first physical-phone timing sample with zero beyond-viewport pages showed cold-composition stalls. Stable page keys and SaveableStateHolder preserve view state. Inactive preview lifecycles are capped at CREATED, stopping lifecycle-aware collection and disabling their Back handlers. Preview touch actions and semantics are blocked. A preview cannot consume a contextual mission/route request. SIM starts its expensive Filament renderer only after arriving, retains that one renderer during departure, and releases it when fully outside the viewport; prepared previews do not start additional scenes. Destination changes produce no runtime commands. Back closes mission/route detail before normal exit handling.

## Runtime and contract review

The native Android theme uses a dark starting window matching Compose background `#0A0E1A`, with light system-bar icons. The Android 12+ splash background uses the same color. This corrects the observed white startup flash from the previous light native theme. It adds no launch delay and does not gate runtime startup. See [Android splash documentation](https://developer.android.com/develop/ui/views/launch/splash-screen).

Eligible regions include Cockpit's large passive instrument panel and non-mission status text, plus Control's phone-tilt preview. The initial header-only affordance was too narrow in user testing. Mission rows/actions, charts, sliders, calibration controls and the SIM camera are not registered as swipe areas.

The navigation layer does not own or gate AppRuntime, sensors, custom input, RPM overrides, recording, physics, networking, or authority. Canonical armed phone input, local takeoff steering, GCS mission exclusions, background suspension, and service retention remain governed by [ADR-0005](0005-canonical-phone-sensor-control.md) and the [runtime lifecycle contract](../runtime-lifecycle.md). Persisting a tab or display setting restores presentation only.

MAVLink parsing, identity, advertised capabilities, ACK behavior, mission execution, units and frames are unchanged. Existing arm/disarm, takeoff/land, start/stop, failure reset and recording actions retain their engine/service paths. Root user guidance describes the new navigation and setting; the Obsidian design specification links back to canonical root documents.

## Verification scope

Tap-only exclusions use local horizontal drag recognition to cancel an in-bounds press after touch slop. Exclusion alone is insufficient: Compose can treat a drag that stays inside a wide button as a tap. Sliders, switches and fields retain their own gestures; vertical scrolling still wins. The Android regression verifies both cancellation on horizontal drag and activation on a subsequent ordinary tap.

Focused unit tests cover direction, no-wrap endpoints, short/reversed gestures, direction locking, ambiguous starts, fast flicks, multi-touch, child consumption and cancellation. Compose instrumentation tests exercise actual pointer dispatch through a competing vertical-scroll parent, diagonal drift, local interactive controls, consecutive navigation, movement while the finger is held, cancellation settling, and interruption of a running animation. Existing phone-sensor/runtime regression tests remain required. Lint, debug build and bounded phone interaction evidence are recorded separately. A single device check cannot qualify all fonts, navigation modes, TalkBack, cutouts or multi-window variants.

## Responsiveness follow-up

The initial implementation passed long, straight scripted gestures but required repeated attempts in natural user testing. Its 18%-of-screen distance, strict early diagonal cancellation, Main-pass scroll arbitration and animation gating were not an adequate acceptance model. The revised detector follows [Compose event-pass and consumption semantics](https://developer.android.com/develop/ui/compose/touch-input/pointer-input/understand-gestures) and uses the [AndroidX velocity tracker](https://github.com/androidx/androidx/blob/androidx-main/compose/ui/ui/src/commonMain/kotlin/androidx/compose/ui/input/pointer/util/VelocityTracker.kt). The explicit passive-area contract is retained, with corrected recognition and dispatch.

The user then requested smoother motion across all screens. Finger-following feedback and interruptible spring settling follow the principles in [Compose gesture animation guidance](https://developer.android.com/develop/ui/compose/animation/advanced). Recognition alone is not sufficient evidence of smooth visual interaction.

On 2026-10-11, the user rejected the first motion revision as still not fluid. The 96 dp resistance made the screen lag behind the finger, and changing selection reset the layer to a fixed 48 dp entry offset: a visual discontinuity even when all gesture tests passed. The replacement uses [Compose's pager layout](https://developer.android.com/develop/ui/compose/layouts/pager), with explicit guards for flight controls, inactive previews and expensive renderer startup. Tests must assert one-to-one movement and unchanged visual position at commit, not just successful navigation or a nonzero offset.
